# test-scenarios 스킬

이슈 번호($ARGUMENTS)를 입력받아 아래 7단계를 순서대로 실행한다.
각 단계에서 개발자 승인이 필요한 경우 반드시 멈추고 대기한다.

---

## 준비: 컨텍스트 수집

단계를 시작하기 전에 다음 세 가지를 병렬로 읽는다:

1. `gh issue view $ARGUMENTS --repo zzgh06/ccwork` — 이슈 제목, 설명, AC 목록
2. `docs/features/tag/prd.md` — 유저 스토리, 기술 제약
3. 코드베이스 패턴 파악
   - `src/types/note.ts` — 도메인 타입
   - `src/api/notes.ts` — API 함수 시그니처 패턴
   - `src/context/NotesContext.tsx` — Context 메서드 패턴
   - `src/components/` — Props 인터페이스 패턴

---

## 1단계 — 시그니처 확정

수집한 컨텍스트를 바탕으로 **이 이슈에서 새로 생기거나 변경되는 것**만 추출한다.

출력 형식:

```
### 타입 변경
// 기존 타입에서 무엇이 추가/변경되는지
interface XxxProps { ... }   // 변경 전 → 변경 후

### 새 컴포넌트 Props (해당하는 경우)
interface XxxProps {
  propName: type;
}

### 함수 시그니처 (해당하는 경우)
// 함수명(파라미터: 타입): 반환타입
// 에러 케이스: 어떤 상황에서 throw

### Context 메서드 변경 (해당하는 경우)
// 기존 시그니처 → 변경 후 시그니처
```

규칙:

- 구현 코드(함수 body, JSX)는 절대 작성하지 않는다
- 기존 패턴(`handleXxx`, `onXxx`, `fetch/create/update/delete` 동사)을 그대로 따른다
- 이슈 범위를 벗어나는 타입/함수는 포함하지 않는다

---

## 2단계 — 시그니처 검토 요청

1단계 결과를 출력하고 아래 메시지로 멈춘다:

> **[검토 요청]** 위 시그니처를 확인해주세요.
> 수정 사항이 있으면 알려주세요. 승인하시면 "승인" 또는 "ok"라고 입력해주세요.

승인 전까지 3단계로 넘어가지 않는다.

---

## 3단계 — 시그니처 문서 저장

승인된 시그니처를 `docs/features/tag/issue-$ARGUMENTS.md` 파일 **상단**에 기록한다.

파일이 이미 존재하면 기존 내용을 지우지 않고, 시그니처 섹션을 맨 위에 삽입한다.

```markdown
# Issue $ARGUMENTS — 시그니처

> 승인일: YYYY-MM-DD

## 타입 변경

...

## 컴포넌트 Props

...

## 함수 시그니처

...

---
```

---

## 4단계 — 테스트 시나리오 도출

확정된 시그니처와 이슈 AC를 기반으로 시나리오를 도출한다.

**분류 기준**:

- **정상**: 올바른 입력으로 기대 동작이 수행되는 경우
- **경계**: 경계값(빈 배열, 최대 길이, 0 등)에서의 동작
- **예외**: 잘못된 입력, 실패 케이스, 사이드이펙트 없음 확인

**형식** (한 줄에 하나):

```
[정상] 함수명/컴포넌트명 — should [기대동작] when [조건]
[경계] 함수명/컴포넌트명 — should [기대동작] when [조건]
[예외] 함수명/컴포넌트명 — should [기대동작] when [조건]
```

**예시**:

```
[정상] NoteItem — should render tag chips when tags is ["react", "study"]
[경계] NoteItem — should not render tag area when tags is []
[예외] TagInput — should not add tag when input is whitespace only
```

규칙:

- 테스트 코드(describe, it, expect)는 작성하지 않는다
- AC 항목 하나당 최소 1개 시나리오가 대응되어야 한다
- 시나리오 수는 많을수록 좋지만, AC 커버리지가 우선이다

---

## 5단계 — 시나리오 문서 저장

도출된 시나리오를 `docs/features/tag/issue-$ARGUMENTS.md` 하단에 추가한다.

```markdown
## 테스트 시나리오

### 정상

- [정상] ...
- [정상] ...

### 경계

- [경계] ...

### 예외

- [예외] ...
```

---

## 6단계 — AC 커버리지 대조

```bash
gh issue view $ARGUMENTS --repo zzgh06/ccwork
```

AC 항목을 읽고 각 항목에 대응하는 시나리오가 있는지 표로 출력한다:

| AC 항목 | 커버하는 시나리오 | 커버 여부 |
| ------- | ----------------- | --------- |
| ...     | ...               | ✅ / ❌   |

- ❌ 항목이 있으면 즉시 시나리오를 추가하고 표와 문서를 업데이트한다
- 모든 AC가 ✅가 될 때까지 반복한다
- 완성된 커버리지 표를 `docs/features/tag/issue-$ARGUMENTS.md` 하단에 `## AC 커버리지` 섹션으로 저장한다

---

## 7단계 — 시나리오 검토 요청

최종 시나리오 목록을 출력하고 아래 메시지로 멈춘다:

> **[검토 요청]** `docs/features/tag/issue-$ARGUMENTS.md`에 시나리오가 저장되었습니다.
> 추가하거나 수정할 시나리오가 있으면 알려주세요.
> 승인하시면 "승인" 또는 "ok"라고 입력해주세요.
>
> 승인 후에는 이 시나리오를 기반으로 `/test-write $ARGUMENTS` 로 테스트 코드를 작성할 수 있습니다.

승인 전까지 테스트 코드 작성이나 구현 코드 작업을 시작하지 않는다.
