# TDD Green — 최소 구현으로 테스트 통과시키기

## 입력

`$ARGUMENTS`로 이슈 번호를 받는다.

```
/tdd-green 5
```

이슈 문서 경로: `docs/features/tag/issue-{$ARGUMENTS}.md`

---

## 핵심 원칙

① **최소 구현 — Fake it till you make it**
하드코딩으로 통과시켜도 Green은 Green이다. 테스트가 요구하는 것만 구현하고,
일반화(generalize)는 Refactor 단계에서 한다.
예: `return ['react']` 같은 임시 반환값도 허용.

② **테스트 파일은 읽기 전용**
테스트 파일은 읽기 전용이다. 통과시키기 어려워서 테스트를 고치고 싶은 충동이
들면 멈춘다. 그건 구현 문제가 아니라 시나리오 문제이므로, test-scenarios 단계로
돌아가야 한다. 테스트의 의도를 잘못 읽었다고 판단되면 사용자에게 확인한다.

③ **피드백 루프 — 최대 5회**
테스트 하나를 통과시키기 위해 수정 → 실행을 최대 5회 반복한다.
5회 초과 시 에러 원인과 현재 코드를 개발자에게 보고하고 중단한다.
단일 파일 먼저(`npx vitest run 파일경로`), 통과 후 전체(`npm test`)로 회귀 검사.

④ **불필요한 방어 코드 금지**
테스트가 요구하지 않는 null 체크, try-catch, 기본값 처리를 추가하지 않는다.
테스트가 없는 경로를 미리 방어하는 코드는 다음 이슈에서 작성한다.

⑤ **디자인 스펙 우선, 임의 스타일 금지**
UI 컴포넌트 구현 시 디자인 문서에 명시된 Tailwind 클래스, 레이아웃, 상태별 표현을
그대로 적용한다. 디자인 문서에 없는 색상, 간격, hover·focus·애니메이션 등 일절 추가 금지.
디자인 스펙과 테스트가 충돌하면 테스트를 우선 통과시킨 뒤 개발자에게 충돌 사실을 보고한다.

⑥ **회귀 확인은 매번**
새 코드 한 줄이 기존 테스트를 깨뜨릴 수 있다. 시나리오 하나를 통과시킬 때마다
`npm test` 전체를 1회 실행해 기존 테스트가 여전히 통과하는지 확인한다.
기존 테스트가 새로 실패하면 해당 구현을 즉시 되돌리고 원인을 분석한다.

⑦ **의존성 순서 구현**
구현 순서: `타입 변경` → `db.json` → `API/Context` → `UI 컴포넌트`
UI 테스트는 올바른 타입에 의존하므로 상위 레이어부터 처리해야
하위 레이어 테스트가 안정적으로 실패→통과 전환된다.

⑧ **TypeScript 컴파일 우선**
컴파일 에러가 있으면 모든 테스트가 실패한다. 특정 테스트를 공략하기 전에
먼저 컴파일을 통과시킨다. 컴파일 에러 해결이 피드백 루프의 첫 번째 우선순위다.

⑨ **테스트 하나씩, 동시 통과 금지**
한 번의 구현으로 여러 테스트를 동시에 통과시키려 하지 않는다.
의도치 않게 여러 테스트가 함께 통과되는 것은 허용하지만,
그것을 목표로 구현하면 Red-Green 사이클의 피드백이 사라진다.

## 파이프라인

```
1. npm test → 실패 목록 파악
      ↓
2. collect 실패 감지 → 필요 시 stub 생성
      ↓
3. 디자인 컨텍스트 로드
      ↓
┌────────────────────────────────────────────────────────┐
│  실패 테스트 하나씩 반복                                │
│   4. 최소 구현 코드 작성 (의존성 순서 준수)            │
│   5. npx vitest run 파일 → 통과 확인                   │
│      npm test → 회귀 확인 (최대 5회 피드백 루프)       │
│   6. 이슈 문서 해당 항목 [x] 체크                      │
└────────────────────────────────────────────────────────┘
      ↓
7. 전체 통과 후 커버리지 측정 (npm run test:coverage)
      ↓
8. 결과 요약 보고
```

---

## 단계별 상세

### 1단계 — npm test 실행, 실패 목록 파악

```bash
npm test
```

실패 테스트 목록을 확인한다. 각 실패 항목의 파일 경로와 `it` 블록 이름을 기록한다.

---

### 2단계 — collect 실패 감지

vitest가 `Cannot find module` 에러를 보고하면서 Tests 수가
이슈 문서 체크박스(`- [ ]`) 총 건수보다 적으면, import 대상 모듈이 없는 것이다.

```bash
# 이슈 문서의 체크박스 수
grep -c '\- \[ \]' docs/features/tag/issue-{N}.md

# vitest가 인식한 Tests 수
npm test 2>&1 | grep 'Tests'
```

불일치 시 시그니처만 있는 stub 파일을 생성해 전체 테스트가 인식되도록 한다.

```typescript
// stub 예시 — src/api/tags.ts
export function addTag(_tags: string[], _tag: string): string[] {
  throw new Error('not implemented');
}
export function removeTag(_tags: string[], _tag: string): string[] {
  throw new Error('not implemented');
}
```

stub 생성 후 `npm test`를 다시 실행해 모든 테스트가 인식되는지 확인한다.

---

### 3단계 — 디자인 컨텍스트 로드

UI 컴포넌트를 구현하기 전에 시각적 스펙을 파악한다.

우선순위 순서로 확인:

1. `docs/design-system/` 디렉토리 또는 `docs/design-system.md` → 색상, 간격, 레이아웃, 상태별 표현 파악
   없으면 CLAUDE.md의 디자인 시스템 섹션 확인
2. `docs/features/{feature}/issue-{N}.md`의 "디자인 참고" 섹션 (있으면 함께 확인)
3. `CLAUDE.md` 스타일링 컨벤션 (Tailwind 버전, 금지 패턴 등)

디자인 문서가 전혀 없으면 이 단계를 건너뛰고 CLAUDE.md 컨벤션만 따른다.

---

### 4단계 — 최소 구현 (의존성 순서 준수)

구현 순서: `타입 변경` → `db.json` → `API/Context` → `UI 컴포넌트`

TypeScript 컴파일 에러가 있으면 이 단계 진입 전에 먼저 해결한다.

| 대상 유형   | 확인할 것                          | 구현 방향                                              |
| ----------- | ---------------------------------- | ------------------------------------------------------ |
| 타입 변경   | 인터페이스 필드                    | 필드 추가만, 기존 구조 유지                            |
| 컴포넌트    | RTL 쿼리(`getByRole`, `getByText`) | 해당 role/text를 가진 최소 마크업 + 디자인 스펙 클래스 |
| 순수 함수   | `expect` 기대값                    | 그 값만 반환하는 최소 로직                             |
| db.json     | `toHaveProperty` 검사              | 해당 필드 추가                                         |
| Context/API | POST body, 반환값                  | 해당 필드 포함한 최소 변경                             |

---

### 5단계 — 피드백 루프 (최대 5회)

```bash
npx vitest run src/경로/파일.test.tsx  # 빠른 단일 파일 확인
npm test                               # 통과 후 전체 회귀 확인
```

실패 시 에러 유형별 원인 파악:

| 에러 메시지                        | 원인                             |
| ---------------------------------- | -------------------------------- |
| `Unable to find element`           | DOM 구조 또는 텍스트 불일치      |
| `Expected [] toEqual [...]`        | 반환값 불일치                    |
| `TypeError: xxx is not a function` | 함수 미존재 또는 시그니처 불일치 |
| `Property does not exist`          | 타입 미추가                      |

5회 초과 후에도 실패하면 에러 메시지 전문, 현재 구현 코드, 분석한 원인을 개발자에게 보고하고 중단한다.

---

### 6단계 — 이슈 문서 체크박스 업데이트

```markdown
<!-- 변경 전 -->

- [ ] [정상] NoteItem — should render tag chips when note.tags is ["react", "study"]

<!-- 변경 후 -->

- [x] [정상] NoteItem — should render tag chips when note.tags is ["react", "study"]
```

---

### 7단계 — 다음 실패 테스트로 이동

이슈 문서 순서를 따라 (`[정상]` → `[경계]` → `[예외]`) 4단계부터 반복한다.
이전 구현으로 이미 통과한 테스트는 건너뛴다.

---

### 8단계 — 커버리지 측정

```bash
npm run test:coverage
```

결과 요약에는 File과 % Stmts 두 컬럼만 추출해 참고용으로 표시한다.
미커버 라인이 이슈 시나리오에서 다루지 않은 케이스인지 판단해 개발자에게 보고한다.
커버리지를 올리기 위한 테스트 추가는 금지. 참고용으로만 활용한다.

## 자주 하는 실수

### 1. 테스트를 고쳐서 통과시킨다

```typescript
// ❌ assertion을 약하게 바꿔 통과 유도
expect(screen.queryByText('react')).toBeDefined(); // null도 통과
// ✅ 구현 파일을 수정해 테스트를 통과시킨다
```

통과시키기 어렵다면 test-scenarios 단계로 돌아가거나 사용자에게 확인한다.

### 2. 다음 테스트를 미리 구현한다

지금 실패한 테스트 하나에만 집중한다. "어차피 다음에 필요할 것 같아서" 추가하는
코드는 Green 단계의 피드백 루프를 깨뜨린다.

### 3. 방어 코드를 미리 추가한다

```typescript
// ❌ 테스트가 요구하지 않는 null 체크
function getTags(note: Note): string[] {
  if (!note || !note.tags) return []; // 테스트에 없는 경로
  return note.tags;
}
// ✅ 테스트가 요구하는 것만
function getTags(note: Note): string[] {
  return note.tags;
}
```

### 4. 디자인 스펙에 없는 스타일을 추가한다

```tsx
// ❌ 스펙에 없는 hover 효과, 아이콘, 마진 임의 추가
<span className="tag-chip hover:opacity-80 mr-2 cursor-pointer">
// ✅ 디자인 문서에 명시된 클래스만 사용
<span className="...스펙에 있는 클래스만...">
```

### 5. collect 실패 상태에서 구현을 시작한다

vitest가 일부 테스트를 인식조차 못하는 상태에서 구현을 시작하면 전체 시나리오
커버 여부를 알 수 없다. 먼저 stub으로 전체 테스트를 인식시킨 뒤 구현한다.

### 6. 회귀를 발견하고도 넘어간다

새 테스트가 통과했더라도 기존 테스트가 깨졌으면 완료가 아니다.
즉시 구현을 되돌리고 원인을 분석한다.

### 7. 5회 초과 후에도 계속 시도한다

5회 안에 통과하지 못하면 혼자 계속 시도하지 않는다.
에러 메시지 전문과 현재 코드를 개발자에게 보고하고 중단한다.

### 8. 타입/컴파일 에러를 무시하고 특정 테스트를 공략한다

컴파일 에러가 있으면 모든 테스트가 실패한다. 특정 테스트 결과가 의미 없어지므로,
컴파일을 먼저 통과시킨다.

### 9. UI 구현을 타입 변경보다 먼저 한다

`Note` 타입에 `tags` 필드가 없는 상태에서 `NoteItem`을 구현하면 TypeScript 에러와
테스트 실패가 섞여 원인 파악이 어려워진다.
의존성 순서(`타입 → db.json → API → UI`)를 반드시 지킨다.

### 10. 테스트에 없는 기능을 추가한다

"이 컴포넌트라면 검색 기능도 있어야 할 것 같다"는 판단은 Green 단계에서 하지 않는다.
테스트에 없는 기능은 존재하지 않는 요구사항이다.
다음 이슈에서 시나리오를 먼저 작성한 뒤 구현한다.

### 11. 디자인 문서에 없는 hover·focus·애니메이션을 추가한다

```tsx
// ❌ 디자인 문서에 없는 인터랙션 임의 추가
<span className="tag-chip transition-opacity hover:opacity-70 focus:ring-2 animate-fade-in">
// ✅ 문서에 명시된 것만
<span className="...스펙에 있는 클래스만...">
```

"더 자연스러워 보이기 위해" 추가하는 인터랙션은 디자인 결정이지 구현 결정이 아니다.
디자인 문서에 없으면 추가하지 않는다.

### 12. 회귀 확인을 생략하고 다음 시나리오로 넘어간다

빠르게 진행하고 싶어서 `npm test` 전체 실행을 건너뛰는 경우가 있다.
그러나 새 코드 한 줄이 무관해 보이는 기존 테스트를 깨뜨릴 수 있다.
시나리오 하나 통과 → `npm test` 전체 1회는 생략 없이 반드시 지킨다.

### 13. 커버리지 100%를 목표로 테스트를 추가한다

커버리지 리포트에서 미커버 라인을 보면 채우고 싶은 충동이 생긴다.
Green 단계의 커버리지 측정은 "시나리오에서 빠진 케이스가 있는지" 파악하는 참고용이다.
커버리지를 올리기 위한 테스트 추가는 이 단계에서 하지 않는다.
추가가 필요하다고 판단되면 개발자에게 보고하고 test-scenarios 단계로 돌아간다.

**시나리오:** {통과수}/{전체수} 통과 — {이슈명} 전체 시나리오 완료

**회귀:** 없음 — 각 시나리오 통과 후 `npm test` 전체 실행, 기존 테스트 영향 없음

| 파일 | 변경 내용 |

| `src/components/NoteItem.tsx` | 태그 칩 목록 렌더링 추가 |
| `db.json` | 기존 노트에 `"tags": []` 추가 |

**커버리지 (참고용)**
| 파일 | % Stmts |
|------|---------|
| All files | 13.13 |
| NoteItem.tsx | 90.00 |
