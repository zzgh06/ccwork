# TDD Refactor — 테스트를 지키며 코드 구조 개선하기

## 입력

`$ARGUMENTS`로 이슈 번호를 받는다.

```
/tdd-refactor 5
```

---

## 핵심 원칙

① **테스트는 안전망이다**
리팩토링은 외부 동작을 바꾸지 않는 내부 구조 개선이다. 모든 변경은 테스트가
깨지지 않는 범위 안에서만 허용된다. 테스트가 깨지면 즉시 롤백하고 다른 접근을 찾는다.

② **하나씩, 확인하며**
여러 개선을 한꺼번에 적용하지 않는다. 하나의 리팩토링 → `npm test` → 통과 확인 → 다음.
이 순서를 지켜야 어떤 변경이 테스트를 깨뜨렸는지 즉시 알 수 있다.

③ **기능 추가 금지**
"어차피 다음에 필요할 것 같아서" 추가하는 코드는 리팩토링이 아니라 구현이다.
새 기능, 새 props, 새 API 함수는 다음 이슈에서 시나리오를 먼저 작성한 뒤 진행한다.

④ **테스트 파일은 읽기 전용**
테스트 코드도 리팩토링 대상이 될 수 있지만, 이 스킬은 구현 코드 개선에만 집중한다.
테스트 파일 수정이 필요하다고 판단되면 개발자에게 먼저 보고하고 승인을 받는다.

⑤ **CLAUDE.md 컨벤션 우선**
코드 개선 방향이 여러 가지일 때는 프로젝트 컨벤션(네이밍, 패턴, 구조)에 맞는 방향을 선택한다.
컨벤션과 충돌하는 "더 나은" 패턴은 이 이슈 범위에서 적용하지 않는다.

⑥ **테스트가 깨지면 즉시 롤백**
테스트가 실패하는 순간 더 이상 진행하지 않는다. 변경한 파일을 즉시 원상복구하고
왜 깨졌는지 분석한다. "조금만 더 고치면 될 것 같다"는 판단으로 계속 수정하지 않는다.
롤백 후 다른 접근으로 같은 목표를 달성하거나, 방법이 없으면 해당 항목을 건너뛰고 개발자에게 보고한다.

⑦ **대상 파일 범위 준수**
`git diff main...HEAD --name-only -- src/`로 추출된 파일만 수정한다.
범위 밖 파일을 수정해야 개선이 가능하다면 개발자에게 보고하고 결정을 위임한다.

## 파이프라인

```
1. CLAUDE.md 읽기 → 프로젝트 컨벤션 파악
      ↓
2. npm test → 전체 통과 확인 (통과 아니면 중단)
      ↓
3. 대상 파일 추출 (git diff, 테스트 파일 제외)
      ↓
4. 범용 점검 기준으로 개선 후보 목록 작성
      ↓
5. [검토 요청] 개발자 승인 대기
      ↓
┌────────────────────────────────────────────────────────┐
│  승인된 개선 항목 하나씩 반복                          │
│   6. 하나의 개선 적용                                  │
│   7. npm test → 통과 확인                              │
│   8. 깨지면 즉시 롤백 후 다른 접근 시도               │
└────────────────────────────────────────────────────────┘
      ↓
9. 리팩토링 전후 변경 요약 보고
```

## 단계별 상세

### 1단계 — CLAUDE.md 읽기

```
CLAUDE.md (프로젝트 루트 + ~/.claude/CLAUDE.md)
```

다음 섹션을 중점적으로 파악한다:

- 네이밍 패턴 (`handleXxx`, `onXxx`, `fetchXxx` 등)
- 컴포넌트 구조 패턴 (Props 인터페이스 위치, export 방식)
- 상태 관리 레이어 분리 원칙
- 금지 패턴 (any 타입, 특정 라이브러리 직접 호출 등)

---

### 2단계 — npm test 실행

```bash
npm test
```

모든 테스트가 통과해야 리팩토링을 시작할 수 있다.
실패 테스트가 있으면 **중단**하고 개발자에게 보고한다:

> **[중단]** 현재 `N`개의 테스트가 실패 중입니다.
> Green 단계에서 모든 테스트를 통과시킨 뒤 Refactor 단계를 시작해주세요.
> 실패 목록: ...

---

### 3단계 — 대상 파일 추출

```bash
git diff main...HEAD --name-only -- src/
```

출력 결과에서 테스트 파일(`*.test.ts`, `*.test.tsx`)을 제외한다.
남은 파일이 이 이슈에서 리팩토링 가능한 대상 목록이다.

대상 파일이 없으면(모두 테스트 파일이거나 변경 파일 없음) 개발자에게 보고하고 종료한다.

---

### 4단계 — 범용 점검 기준으로 개선 후보 목록 작성

대상 파일 각각을 읽고 아래 기준으로 검토한다.
기준에 해당하는 항목만 개선 후보로 올린다 — 억지로 채울 필요 없다.

#### 점검 기준

| 기준                        | 확인 방법                                                                     |
| --------------------------- | ----------------------------------------------------------------------------- |
| **중복 제거**               | 같은 로직이 2곳 이상 반복되는가                                               |
| **네이밍 명확성**           | 변수명/함수명이 의도를 드러내는가 (`data`, `temp`, `flag` 같은 모호한 이름)   |
| **단일 책임**               | 하나의 함수/컴포넌트가 너무 많은 일을 하는가 (30줄 이상 JSX, 3개 이상 관심사) |
| **불필요한 복잡도**         | 매직 넘버, 4단 이상 중첩, 사용하지 않는 변수/import                           |
| **CLAUDE.md 컨벤션 불일치** | 프로젝트 패턴과 어긋나는 코드 (default export 사용, Props 인터페이스 위치 등) |

개선 후보 형식:

```
파일: src/components/NoteItem.tsx
항목: 네이밍 명확성
현재: const x = note.tags.filter(...)
제안: const visibleTags = note.tags.filter(...)
이유: 변수가 보여줄 태그 목록임을 이름에서 알 수 없음
```

---

### 5단계 — 개발자 승인 대기

개선 후보 목록 전체를 출력한 뒤 멈춘다:

> **[검토 요청]** 아래 리팩토링 항목을 확인해주세요.
> 적용할 항목에 번호로 응답하거나, "전체 승인"/"건너뛰기"로 응답해주세요.

개선 후보가 없을 경우:

> **[완료]** 점검 기준에 해당하는 개선 항목이 없습니다.
> 현재 코드는 프로젝트 컨벤션에 부합합니다.

---

### 6단계 — 개선 적용 (하나씩)

승인된 항목을 **하나씩** 적용한다.

```bash
# 단일 파일 빠른 확인
npx vitest run src/경로/파일.test.tsx

# 전체 회귀 확인
npm test
```

테스트가 깨지면 즉시 롤백:

1. 변경한 파일을 원상복구한다
2. 왜 테스트가 깨졌는지 분석한다
3. 다른 방법으로 같은 목표를 달성할 수 있는지 시도한다
4. 방법이 없으면 해당 항목을 건너뛰고 개발자에게 보고한다

---

### 7단계 — 변경 요약 보고

모든 항목 처리 후 아래 형식으로 보고한다.

**적용된 리팩토링**
| 파일 | 항목 | 변경 내용 |
|------|------|---------|
| `src/components/NoteItem.tsx` | 네이밍 명확성 | `x` → `visibleTags` |
| `src/api/notes.ts` | 중복 제거 | `buildUrl` 헬퍼 추출 |

**롤백된 시도**
| 파일 | 항목 | 시도한 변경 | 롤백 사유 |
|------|------|------------|---------|
| `src/context/NotesContext.tsx` | 단일 책임 분리 | `useNotesState` 훅 분리 시도 | 기존 테스트 `mockContext` 구조 변경 필요 |

**남은 후보** (승인받았으나 미처리 또는 범위 밖으로 보류)
| 파일 | 항목 | 보류 사유 |
|------|------|---------|
| `src/api/notes.ts` | 에러 메시지 통일 | 이 이슈 범위(git diff) 밖 파일 영향 |

**최종 테스트 결과**

```
테스트: N개 통과 / 0개 실패
```

**다음 단계 제안**
롤백되거나 보류된 항목 중 후속 작업이 필요한 것을 제안한다:

- 별도 이슈로 다룰 만한 구조 개선이 있으면 이슈 제목 후보를 함께 제시한다
- 테스트 추가가 선행되어야 리팩토링 가능한 항목은 test-scenarios 단계 재진입을 권고한다

## 자주 하는 실수

### 1. 테스트가 없는 부분을 "개선"하면서 동작을 바꾼다

테스트가 없는 코드 경로를 수정할 때는 특히 주의한다.
테스트가 없다고 동작 변경이 허용되는 게 아니다. 테스트가 없는 경로는
다음 이슈에서 시나리오를 먼저 작성한 뒤 다룬다.

### 2. 여러 개선을 한 번에 커밋한다

개선 하나 → 테스트 → 통과의 사이클 없이 여러 개를 묶으면,
어떤 변경이 문제를 일으켰는지 추적이 어려워진다.

### 3. "더 나은 패턴"을 이유로 기존 컨벤션을 무시한다

프로젝트에 이미 확립된 패턴이 있다면 이 이슈 범위에서 바꾸지 않는다.
컨벤션 변경은 별도 이슈로 전체 코드베이스에 일관되게 적용해야 한다.

### 4. 대상 파일 범위 밖을 수정한다

`git diff main...HEAD` 결과 밖의 파일을 수정하면 이 이슈와 무관한 변경이
같은 브랜치에 섞이게 된다. 범위 밖 개선은 개발자에게 먼저 물어본다.

### 5. 리팩토링 중에 새 기능을 끼워넣는다

"어차피 여기 손대는 김에 이것도 추가하자"는 생각은 위험하다.
Red-Green-Refactor 사이클의 명확한 경계가 흐려지고, 테스트 없는 기능이 생긴다.
